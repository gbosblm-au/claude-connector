# Hotfix: WO-2026-11-21-02 (module_write registration path)

For the live connector branch. It is built on the `src` you sent on
2026-11-21 plus that evening's write-path hotfix (restored imports in
`skill-content.js` and `skill.js`, and the `/restore-modules` claim in
`skill-modular.js`). Those three files are included, so this zip stands alone.
**Bump the connector version in your `package.json` when you deploy**, because
that file was not in the upload.

No stored registration is changed by deploying this. module_write changes
only what it writes from now on. Repairs are proposed by a read-only report
and applied one module at a time, after Brian approves each one.

## What changed

### Phase P: no registration content is derived from the module body
The changes are in `src/tools/manifest-fragments.js`.

- The body miner is removed: `tokensOf`, `mineBodyContent` and heading
  derivation (P1).
- **Triggers** come from the frontmatter `triggers:` block if it is present
  and non-empty, used verbatim (case and every character kept). Otherwise
  they come from `manifest_entry.triggers`. Otherwise the set is empty, with
  `triggers_source: "none"` and a warning naming the module (P2, P3).
- **Lint.** A keyword is dropped if it is a directory on the module's path,
  the file name, or `module`/`skill`/`note` (P4). A phrase is dropped unless
  it meets all of these (P5):
  - it has two or more words;
  - it is at least 12 characters;
  - it has no stopword at either end;
  - it is not part of another phrase on the module.

  Every drop is listed in `registration_warnings`, and nothing is rewritten.
- **provides** comes from frontmatter `provides:`, then
  `manifest_entry.provides`, otherwise it is empty with a warning (P6).
- **title** comes from frontmatter `title:`, then `manifest_entry.title`,
  otherwise the id (P7).
- **version** comes from frontmatter `version:` at every write. Otherwise it
  is left out, never invented and never carried forward.
- **line_count_estimate** is counted from the written file at every write,
  using the compile's own counting rule (P8).
- **task_class** is only what was supplied (P10).
- **Encoding (P9).** Every string must round-trip through UTF-8 unchanged,
  and a frontmatter value must appear verbatim in the frontmatter it was read
  from. A failure refuses the write with `registration_encoding_loss`.
- **Frontmatter reader.** A new verbatim reader, `readRegistrationFrontmatter`,
  reads:
  - inline `[arrays]` with quoted items;
  - block lists;
  - `triggers:` mappings, including one-line `{ keywords: [...] }`;
  - `triggers.keywords:` keys.

  An unreadable `triggers:` value produces a warning. The old
  `parseModuleFrontmatter` is unchanged for its other users.

### Phase Q: an existing registration is updated, never minted again
The changes are in `src/tools/module-files.js` (`registrationPlan`) and
`skill-content.js`.

Before any file is touched, every registration of the id is enumerated over
the duplicate guard's own snapshot (the compile's resolver) (Q1). Then:

- **Q2.** Registered at this path: that registration is updated in place, in
  whichever fragment holds it.
- **Q3.** Registered at another path: refused with `id_registered_elsewhere`,
  naming every registration and its path. To proceed, either:
  - pass `acknowledge_existing_registration` (the fragment registration to
    re-point), or
  - quarantine the other file first.
- **Q4.** Registered in `MANIFEST.json` or `MANIFEST_APPEND.json`: no fragment
  registration is written, and the reply names the frozen manifest.
- **Q5.** A new id goes into its category's existing fragment, found by
  `source` or by file name. Before this fix, a fragment without a `source`
  field was missed, and a new one was created beside it.

The dry run reports the same plan and returns the same refusals.

### Phase R: repair report
Run `skill_consistency_audit` with `registration_repair_report: true`. It
lists every fragment registration whose `triggers_source` is absent or
`"derived"`, or that has a phrase failing P5. For each one with defects, it
gives the corrected entry proposed from the module's own frontmatter. An entry
that already passes every rule, such as your two hand corrections (R4), is
listed with **no change proposed**. The report writes nothing. Each row says
how to apply it once Brian approves it.

### Phase S: audit checks
- **C-L** (advisory, never blocks) reports:
  - phrases ending in a stopword;
  - keywords that are a path segment (or `module`/`skill`/`note`);
  - a version that differs from the module's frontmatter;
  - a line count off by more than 20%;
  - `provides` values containing a space;
  - U+FFFD, or a double space in a name field.
- **C-F** now judges each duplicate:
  - `defect_minted_on_write` when more than one registration was created by
    module_write;
  - `defect_fragment_beside_frozen_manifest`;
  - `predates_tool` otherwise.

  Authorship is read, in this order, from:
  1. the new `registered_by: "module_write"` marker;
  2. the H-3 ledger;
  3. the exact key set the old derivation produced.

## Readings of the order you should know about

1. **Lint applies to authored triggers too.** "Verbatim" is read as no
   character change. A frontmatter phrase that fails P5 is still dropped and
   reported. So `Alev Türker` alone (11 characters) is dropped as a phrase but
   kept as a keyword.
2. **"Path segment"** means the directory names, the file name and
   `module`/`skill`/`note`. An abbreviation like `exist` (from
   `exist-attunement-heidegger.md`) cannot be told apart from a topic like
   `heidegger` by rule. Nothing derives keywords from the path any more, so
   `exist` can appear only if an author writes it.
3. **Explicit `manifest_entry` values for title, provides and version** are
   used where the frontmatter is silent. They are explicit input, not
   derivation.
4. **An update with no triggers or provides supplied keeps the existing
   ones.** The same goes for `load_priority`, `always_load`, `depends_on` and
   unmanaged keys. Clearing them as a side effect of a body edit would be a
   dispatch change, which R3 reserves for Brian. To clear them deliberately,
   pass `manifest_entry: { triggers: { keywords: [], phrases: [], task_class: [] }, provides: [] }`.
5. **H-11 intake.** The `triggers` check now **warns** on an empty set
   instead of refusing, per the order's closed decision in section 7. One
   H-11 test case changed accordingly.
6. **Which refusal leads.** Where the other path's file exists,
   `duplicate_id_path` stays first (WO-2026-11-21-01 R2 pins it), with
   `id_registered_elsewhere` listed alongside. Where only a registration
   points there, `id_registered_elsewhere` comes first.
7. **Two earlier tests changed** in `manifest-h2-loop.test.js`: "every H2
   becomes a task class" now asserts that none does, and the exec-loop scan
   accepts zero loops.
